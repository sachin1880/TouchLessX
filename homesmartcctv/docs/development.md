# Development Guide

## Day-to-day backend loop

```bash
cd backend
source .venv/bin/activate
uvicorn app.main:app --reload      # http://localhost:8000, auto-reloads on save
python -m pytest -v                 # 25 tests, needs smarthome_camera_test DB (see README)
```

After changing a SQLAlchemy model, generate and apply a migration:

```bash
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
```

Always read the autogenerated migration before applying it — autogenerate is good at column/table diffs, not always great at things like enum changes or data backfills.

## Day-to-day mobile loop

```bash
cd mobile
npm start                           # Metro bundler
npm run android                     # in another terminal, or npx react-native run-android
```

Before considering any change done:

```bash
npx tsc --noEmit
npx eslint src App.tsx
npx jest
```

If you add a native dependency or touch `android/`, do a full rebuild rather than trusting Metro's fast refresh:

```bash
cd android && ./gradlew assembleDebug
```

## Testing the WebRTC flow end-to-end

A single emulator can't prove the camera↔viewer flow works — you need two independent app instances, logged into the same account, one on each role. Two options:

- **Two emulators.** `avdmanager` wasn't available in the environment this was built in, so a second AVD was created by cloning `~/.android/avd/<name>.avd` and its `.ini` file by hand, editing `AvdId`/`avd.ini.displayname`, and booting with `-port <different port>`. Note that cloning an AVD this way also clones its **userdata partition**, which means any app data (including this app's AsyncStorage — your login/role) comes along with it; `pm clear <package>` resets a cloned instance to a blank slate before picking a different role on it than the original had.
- **One emulator + one real device**, or **two real devices** — simpler if you have the hardware, since there's no AVD cloning involved and you get a real camera feed instead of the emulator's virtual scene.

Either way: both instances need Metro (`adb -s <serial> reverse tcp:8081 tcp:8081`) and the backend needs to be reachable from both (`10.0.2.2` for emulators, your machine's LAN IP for real devices).

## Known gotchas hit while building this

- **`DeviceInfo.getUniqueId()` survives `pm clear`.** It's tied to the Android instance, not app data. Reinstalling/clearing an app and registering again as a *different* account on the *same* emulator will hit the `409 device already registered to another account` path — that's correct behavior, not a bug, but it's surprising the first time. Delete the stale `camera_devices` row (or use a different emulator/device) if you're deliberately testing with multiple accounts.
- **A `useEffect` that depends on frequently-changing state can create a runaway loop.** The heartbeat effect originally depended on the `device` object, which gets a new reference on every heartbeat response — that retriggered the effect, which fired another heartbeat immediately, in a ~30/sec loop instead of the intended 25s interval. Fixed by depending on a stable "have we registered yet" flag instead. Worth remembering as a general pattern: never gate a polling/interval effect on data the poll itself updates.
- **`react-native-webrtc`'s TypeScript types lose the generic `addEventListener` overload** under this project's `moduleResolution: "bundler"` + `customConditions: ["react-native"]` config, because that condition resolves the package to its mixed `.ts`/`.js` source tree rather than its compiled `lib/typescript` declarations, and the source's `EventTarget` base ships as a `.js`+`.d.ts` pair that doesn't carry the overload through. `src/webrtc/rtcEvents.ts` works around it with narrowly-typed wrapper functions — runtime behavior is unaffected, this is a type-checking-only issue.
- **`sudo xcodebuild -license accept`** blocks `git` *and* Homebrew (not just Xcode/iOS builds) on a fresh macOS setup until it's run once, interactively, by a human with the machine's password.
- **A shell redirect (`command > file.log 2>&1 &`) truncated externally (`: > file.log`) doesn't reset the writing process's file offset.** If you truncate a log file that a still-running backgrounded process has open, its next writes land at its old offset, not byte 0 — the file looks empty even though the process is still logging. Don't rely on `: > logfile` to "clear" a log for a live process; restart the process, or read the file without assuming truncation took effect.
